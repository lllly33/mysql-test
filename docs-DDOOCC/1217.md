# 数据库内核优化设计文档：基于高延迟块存储的 B+Tree 并发控制

## 1. 问题背景与分析

*   **硬件瓶颈**：当前存储介质为云盘块存储（ESSD），读写延迟约为 **200µs**，远高于本地 NVMe SSD 的 10µs。
*   **软件痛点**：InnoDB 传统的 B+Tree 在进行 **SMO（结构修改操作，如页分裂/合并）** 时，采用了较为悲观的 **Latch Coupling（锁耦合）** 机制。
*   **核心矛盾**：
    *   在 SMO 发生时，写线程需要持有从根节点到叶子节点的路径锁（X-Latch 或 SX-Latch）。
    *   由于 ESSD I/O 延迟高（200µs），写线程持有锁的时间被物理 I/O 强行拉长。
    *   此时，其他并发的读/写线程试图访问该路径时会被阻塞，导致 CPU 等待（Wait），系统吞吐量（QPS）急剧下降。

## 2. 核心优化策略

### 策略一：引入 B-Link Tree 思想（Side Link 侧向指针）

这是解决 SMO 锁阻塞最有效的方案。通过利用叶子节点的右指针，将“分裂”与“父节点更新”解耦。

* **优化逻辑**：

  *   **读操作去锁化**：查询时，不再严格依赖父节点锁来保证正确性。如果目标 Key 大于当前页面的最大值（High Key），直接通过 `FIL_PAGE_NEXT` 指针跳转到右兄弟节点。
  *   **分裂异步化**：页分裂时，优先完成左右兄弟节点的指针链接（Atomic Link），即可释放锁让读请求通行。父节点的指针更新（这是最耗时的向上传导）可以延迟进行或异步进行。

  > > **<u>Q：为什么这么久以来，b-link的思想没加入mysql的innoDB里？</u>**
  >
  > Lehman 和 Yao 在 1981 年就提出了 Blink-tree（B-link Tree），确实被学术界公认为解决 B+Tree 并发分裂的神器。**PostgreSQL 其实就使用了 Blink-tree 的变种算法**（`nbtree`），但作为数据库界的老大，MySQL (InnoDB) 却迟迟没有全盘采纳。
  >
  > 这并非 MySQL 团队技术不行，而是因为**“工程实现的复杂性”**和**“历史包袱”**，主要体现在以下 5 个核心痛点：
  >
  > ### 1. Next-Key Locking 与 幻读（最核心原因）
  >
  > 这是 InnoDB 和其他数据库最大的区别。
  >
  > *   **Blink-tree 的特点：** 它的核心思想是“允许不一致”。当节点分裂时，父节点指针还没改，但我允许读操作通过右指针（Side Link）飘到新节点去。这要求读操作必须是**无锁**或**极其轻量**的。
  > *   **InnoDB 的包袱：** InnoDB 支持 **Repeatable Read (可重复读)** 隔离级别，并且通过 **Next-Key Lock (间隙锁)** 来解决幻读问题。
  >     *   **冲突点：** 当一个事务锁住了 `(5, 10)` 这个间隙。如果此时 B+Tree 发生了无锁分裂，数据 `8` 被移动到了右边的新节点。
  >     *   **灾难：**原本锁住的“间隙”物理位置变了！那个锁还生效吗？锁管理模块（Lock Manager）怎么知道数据跑到右边去了？
  >     *   **结论：** Blink-tree 的“数据漂移”特性，与 InnoDB 严格的“间隙锁”机制在实现上存在巨大的冲突。要兼容两者，需要重写整个事务锁系统。
  >
  > ### 2. 删除（Merge）操作的噩梦
  >
  > Lehman & Yao 的论文（以及很多后续论文）通常只重点讲 **Split（分裂/插入）** 怎么并发，而对 **Merge（合并/删除）** 往往一笔带过或者说“加锁处理”。
  >
  > *   **现实残酷：** 数据库是长期运行的，有增就有删。
  > *   **并发合并难点：** 如果你要把两个节点合并，你必须锁住这两个节点，**同时**还要去修改父节点删掉一个指针。
  > *   **Blink-tree 的短板：** 在处理合并时，Blink-tree 的右指针机制并不能带来太大的便利，依然需要复杂的加锁（甚至由于右指针的存在，死锁检测变得更麻烦，因为出现了横向依赖）。
  > *   **InnoDB 的选择：** 既然删除无论如何都要加重锁，那为了代码一致性，插入也沿用类似的锁机制（SX 锁）似乎更稳妥。
  >
  > ### 3. ARIES 恢复协议的复杂性
  >
  > 数据库必须保证 ACID，特别是 Crash Recovery（崩溃恢复）。
  >
  > *   **Blink-tree 的状态：** 引入了一种“中间态”——子节点分裂了，指向了兄弟，但父节点还没更新。
  > *   **日志问题：** 如果这时候断电了，Redo Log 怎么记？重启后，怎么知道这个分裂完成了一半？怎么通过日志把父指针补上？
  > *   **InnoDB 的做法：** 采用 **Mini-Transaction (MTR)**。一个 MTR 保证了底层的原子性。现有的 MTR 机制是基于“持有锁”来设计的。如果要换成 Blink-tree 的异步更新父节点，现有的日志恢复逻辑（基于 LSN 和 Page）可能需要大幅重构。
  >
  > ### 4. 索引组织表 (Clustered Index) 的代价
  >
  > *   **PostgreSQL (使用 Blink-tree)：** 是堆表（Heap Table）。索引里只存指针。索引分裂了，数据还在原来的堆文件里没动，代价比较小。
  > *   **MySQL InnoDB：** 是**索引组织表**。数据**就是** B+Tree 的叶子节点。
  >     *   如果叶子节点频繁无锁分裂，涉及大量实际数据的迁移（Data Copy）。
  >     *   在数据迁移过程中，如果有并发的 Update/Delete 操作，由于 Blink-tree 放宽了锁，很难保证数据不丢不乱。
  >
  > ### 5. 既有优化的“够用”原则
  >
  > MySQL 5.7 和 8.0 其实已经做了很多优化，虽然没有用纯粹的 Blink-tree，但效果已经接近了：
  >
  > *   **SX 锁 (Shared-Exclusive)：** 允许读写并发，只阻塞“其他结构变更”。
  > *   **乐观插入：** MySQL 先假设不会分裂，用轻量锁去试。只有真的满了，才回退重来，用大锁。
  > *   **现状：** 在绝大多数场景下（95%），B+Tree 的层高只有 3-4 层，且非叶子节点分裂频率极低。现有的锁耦合（Latch Coupling）加上 SX 锁，性能瓶颈通常卡在 **IO** 和 **行锁（Row Lock）** 上，而不是 B+Tree 的树结构锁上。
  > *   **改造成本：** 既然现在的方案已经能解决 90% 的问题，重写内核去换 Blink-tree 带来的额外收益，可能抵消不了引入新 Bug 的风险（数据库最怕丢数据）。
  >
  > **总结：**
  > MySQL 不用 Blink-tree 是因为它要背负 ACID、间隙锁、崩溃恢复等沉重的历史包袱。而你在比赛中，可以甩掉这些包袱，**专门针对“高延迟 IO”这个场景，把 Blink-tree 的右指针思想发挥到极致**。这正是魔改的价值所在。

### 策略二：优化 Latch Coupling（锁交替/Crabbing）

减少持有上层节点锁的时间。

*   **优化逻辑**：
    *   **标准模式**：Lock Parent -> Lock Child -> Unlock Parent。
    *   **激进模式（配合 B-Link）**：在获得 Child 指针后，**立即**释放 Parent 锁，甚至在读操作中不加 Parent 锁（依赖 Side Link 纠错）。

### 策略三：内存缓冲层（借鉴 Log-Structured/SkipList 思想）

针对 ESSD 的随机写劣势，引入内存缓冲。

* **优化逻辑**：

  *   在 B+Tree 之前引入一个无锁的 SkipList 作为 MemTable。
  *   高并发写入先在内存完成（消除 I/O 延迟导致的锁等待）。
  *   积攒一定量后，批量（Batch）写入 B+Tree，摊薄 SMO 的开销。

  > ### 1. 核心区别：物理页缓存 vs 逻辑写缓冲
  >
  > #### A. MySQL InnoDB Buffer Pool (现有的)
  >
  > *   **本质**：它是**“物理页（Page）”的缓存**。
  > *   **工作方式**：
  >     *   InnoDB 的 B+Tree 是存放在磁盘上的。Buffer Pool 只是把磁盘上 **16KB 的物理页** 原封不动地搬到内存里。
  >     *   当你写入一条数据时，InnoDB 必须先在 Buffer Pool 里找到对应的 **Page**，对这个 Page 加锁（Latch），然后在 Page 内部修改二进制数据，最后标记为“脏页”等待刷盘。
  > *   **赛题中的痛点**：
  >     *   Buffer Pool 确实在内存里，**但是**，为了维持 B+Tree 的严格有序结构，如果 Page 满了，必须触发 **SMO（结构分裂）**。
  >     *   即使在内存里分裂，也需要锁住父节点。如果父节点不在内存里，就要去读 ESSD（200us延迟），这时候锁就被长时间占用了。
  >     *   **总结：Buffer Pool 加速了读，但无法消除 B+Tree 维护结构（Split/Merge）带来的锁开销。**
  >
  > #### B. Skip List Buffer (建议引入的)
  >
  > *   **本质**：它是**“逻辑记录（Key-Value）”的写缓冲**。
  > *   **工作方式**：
  >     *   它不关心磁盘上的 16KB Page 长什么样。它只是内存里的一个链表。
  >     *   当你写入数据时，直接丢进 Skip List，**根本不去碰 B+Tree，也不去碰 Buffer Pool**。
  >     *   Skip List 满了之后，再启动一个后台线程，把里面的数据**批量**合并（Merge）到 B+Tree（Buffer Pool）中。
  > *   **赛题中的作用**：
  >     *   它像一个**“蓄水池”**。
  >     *   它把高并发的“随机写”，拦截下来，变成了内存里的操作（无锁、极快）。
  >     *   它避免了每次写入都触发 B+Tree 的锁竞争。
  >
  > ---
  >
  > ### 2. 为什么它们可以共存？（架构图解）
  >
  > 在优化的架构中，数据流向是这样的：
  >
  > ```mermaid
  > graph LR
  >     A[用户写请求] --> B(Skip List Buffer \n 纯内存/无锁)
  >     B -- 积累到一定量/后台线程 --> C(InnoDB B+Tree \n 在 Buffer Pool 中)
  >     C -- 刷脏页 --> D[ESSD 磁盘]
  > ```
  >
  > **它们的分工：**
  >
  > 1.  **Skip List (MemTable)**：
  >     *   **职责**：**抗写压**。
  >     *   **状态**：存的是最新的、还没来得及合并到 B+Tree 的数据。
  >     *   **优势**：插入不需要磁盘 I/O，不需要处理页分裂，CAS 无锁操作极快。
  >
  > 2.  **Buffer Pool (Page Cache)**：
  >     *   **职责**：**抗读压** + **数据持久化中转**。
  >     *   **状态**：存的是 B+Tree 的全貌。
  >     *   **优势**：利用局部性原理，让读操作尽量命中内存。
  >
  > ---
  >
  > ### 3. 结合赛题：引入 Skip List 到底解决了什么矛盾？
  >
  > 你可能会问：“反正最后都要写进 Buffer Pool 里的 B+Tree，这不多此一举吗？”
  >
  > **答案在于：批量化（Batching）与异步化。**
  >
  > #### 场景对比：
  >
  > *   **原始 MySQL (无 Skip List)**：
  >     *   来了 1000 个插入请求。
  >     *   需要操作 B+Tree 1000 次。
  >     *   可能触发 10 次页分裂（SMO）。
  >     *   每次分裂都要抢锁，如果涉及 ESSD IO，这 1000 个请求全堵在锁上。
  >
  > *   **优化后 (有 Skip List)**：
  >     *   来了 1000 个插入请求。
  >     *   全部写入 Skip List（纳秒级，无锁，无 IO）。**用户立刻得到响应，吞吐量极高。**
  >     *   后台线程醒来，把这 1000 条数据取出来。
  >     *   **一次性** 对 B+Tree 加锁，把这 1000 条填进去（或者利用 Change Buffer 的思想）。
  >     *   **收益**：把 1000 次锁竞争变成 1 次；把零散的 SMO 变成批量的修改。
  >
  > ### 4. 这里的“冲突”其实是资源竞争
  >
  > 如果说有冲突，那唯一的冲突就是 **内存（RAM）**。
  >
  > *   你的服务器内存是有限的。
  > *   Buffer Pool 想占 80%。
  > *   Skip List 也想占内存。
  >
  > **解决办法**：
  >
  > *   控制 Skip List 的大小（比如固定 256MB 或 512MB）。
  > *   一旦 Skip List 满了，必须强制 Flush 到 B+Tree（Buffer Pool），腾出空间。这在数据库领域叫 **"MemTable Flush"**。
  >
  > ### 5. 总结
  >
  > *   **MySQL Buffer Pool** 是为了解决 **“磁盘太慢，读写物理页需要缓存”** 的问题。
  > *   **Skip List Buffer** 是为了解决 **“B+Tree 结构维护太重，写入并发锁竞争太激烈”** 的问题。
  >
  > 实际上，**LSM-Tree（如 RocksDB）** 就是把这个 Skip List 缓冲发挥到极致，甚至放弃了 B+Tree；而你的任务是在不抛弃 B+Tree 的前提下，借鉴这个思想。

## 3. MySQL 8.0.34 代码修改指南

要实现上述思想，需要深入修改 InnoDB 的存储引擎内核。以下是具体的代码文件、函数位置及修改点。

### 组件 A：核心游标遍历 (B-Tree Traversal)

**文件路径**：`storage/innobase/btr/btr0cur.cc`
**核心函数**：`btr_cur_search_to_nth_level`

这是整个优化的**主战场**。该函数负责控制从 Root 到 Leaf 的遍历过程。

* **修改点 1：引入右移逻辑 (B-Link Traversal)**

  * **原逻辑**：严格按照父节点指针向下找。

  * **新逻辑**：在读取 Page 后，增加一个检查：

    ```cpp
    // 伪代码示例
    page_t* page = btr_page_get(block, ...);
    // 获取当前页的最大 Key (Supermum)
    if (target_key > page_get_high_key(page)) {
         // 目标值超出了当前页范围，说明发生了分裂
         // 此时不报错，而是直接向右走
         block = btr_block_get(page_get_next_page_id(page), ...);
         goto process_next_page;
    }
    ```

* **修改点 2：提前释放父节点锁**

  *   **原逻辑**：在 `latch_mode` 较为严格时，会一直持有上层锁。
  *   **新逻辑**：在确认能够读取子节点 Page ID 后，立即释放 `RW_S_LATCH` 或 `RW_SX_LATCH`，减少锁竞争窗口。

### 组件 B：页分裂与结构变更 (SMO Handling)

**文件路径**：`storage/innobase/btr/btr0btr.cc`
**核心函数**：`btr_page_split_and_insert`

该函数负责具体的页面分裂操作。

*   **修改点 1：原子化分裂顺序**
    *   确保分裂步骤符合 **Lehman & Yao** 算法要求：
        1.  分配新页 `NewPage`。
        2.  迁移数据。
        3.  **关键步骤**：先建立 `NewPage` 指向 `OldPage->Next`，再原子更新 `OldPage` 指向 `NewPage`。
    *   这样在写入 ESSD 的过程中，读请求可以通过 OldPage 的 Next 指针找到数据，而不需要被全局锁阻塞。
*   **修改点 2：延迟父指针更新 (Lazy Parent Update)**
    *   尝试将“插入父节点指针”的操作从主分裂流程中解耦，或者将其降级为异步任务（注意：这在 InnoDB 中实现难度较大，需处理崩溃恢复的一致性）。

### 组件 C：页面底层结构 (Page Structure)

**文件路径**：`storage/innobase/page/page0page.cc` & `include/page0page.ic`

*   **关注点**：`FIL_PAGE_NEXT` 和 `FIL_PAGE_PREV`。
*   **修改建议**：无需修改结构本身，但需要确保在 `btr0cur.cc` 中能以极低的开销快速读取这两个字段，以及页面的 `PAGE_SUPERMUM`（最大记录），用于判断是否需要右移。

### 组件 D：Mini-Transaction 锁管理 (MTR)

**文件路径**：`storage/innobase/mtr/mtr0mtr.cc`

*   **修改点**：InnoDB 的锁是挂在 MTR（Mini-Transaction）上的。
*   **新逻辑**：如果要实现“读取子节点后立即释放父节点锁”，可能需要手动调用 `mtr_release_block_at_savepoint` 或修改 MTR 的锁释放规则，允许非栈式的锁释放。

## 4. 预期收益与风险

### 预期收益

*   **QPS 提升**：在 ESSD 高延迟场景下，读写混合场景的吞吐量预计大幅提升（因为写操作不再长时间阻塞读操作）。
*   **CPU 利用率提升**：减少了线程在 Futex/Mutex 上的休眠等待，让 CPU 更多地用于处理逻辑。

### 潜在风险与难点

*   **死锁（Deadlock）**：B-Link 的“自左向右”加锁与 B+Tree 原有的“自底向上/自顶向下”逻辑混合时，极易产生死锁。需严格规定加锁顺序（Ordering）。
*   **数据一致性**：如果在父节点指针未更新时系统崩溃，重启后通过 Root 遍历可能找不到新分裂的节点。需要依赖 `FIL_PAGE_NEXT` 链表进行全表扫描恢复，或者保证 Redo Log 的正确性。

---

## 5. 总结

本方案针对 **ESSD 200µs 延迟** 这一核心约束，放弃了传统的强一致性全局锁方案，转而采用 **B-Link Tree 的“右指针”机制** 来掩盖 I/O 延迟。通过修改 `btr0cur.cc` 的查找逻辑和 `btr0btr.cc` 的分裂逻辑，将原本串行的“锁等待-I/O”过程转化为并行的“无锁读取+后台I/O”，从而实现性能优化。
